# 설계 결정 기록

> 형식: 날짜 — 결정 / 이유 / 버린 대안. 짧게. README "설계 결정" 절의 재료.

### 2026-10-15 — 데모 도메인: 세금 어시스턴트(연말정산)
- **결정**: 데모 에이전트의 도메인은 연말정산 공제 안내. 실연동 없이 mock.
- **이유**: 공제액은 규칙으로 계산되므로 **정답을 코드로 만들 수 있다** → 정답 일치 평가가 가능.
- **버린 대안**: 통신 고객센터 mock(정답 정의가 모호).

### 2026-10-15 — 프로젝트 축: 에이전트가 아니라 평가·관측성·비용
- **결정**: 에이전트는 단순하게, 측정 체계를 주인공으로.
- **이유**: 멀티 에이전트·RAG 자체는 흔한 주제다. 이 프로젝트가 보여 주려는 것은 평가·관측성·비용·배포다.
- **버린 대안**: 또 하나의 RAG 챗봇, 멀티 에이전트 데모.

### 2026-10-27 — 관측 도구: Langfuse (Cloud 무료로 시작 → 마일스톤 6에서 셀프호스트)
- **결정**: Langfuse. LangSmith는 쓰지 않는다.
- **기준**: "현업에서 더 많이 쓰는 것" (본인). 독립적인 점유율 조사는 없음 → 아래 신호로 판단.
- **이유**: ① 오픈소스·LangChain 비종속이라 어느 스택에서도 쓰인다(GitHub 약 2.9만 스타, 2026-06 기준 리뷰). LangSmith는 LangChain/LangGraph 스택 안에서 강함. ② 무료 셀프호스트 가능 — 데이터를 밖으로 내보낼 수 없는 환경(대기업·금융 등)에서도 쓸 수 있는 형태. LangSmith 셀프호스트는 Enterprise 애드온. ③ 마일스톤 6 "Docker 실행"에 그대로 포함 가능.
- **버린 대안**: LangSmith(LangGraph 연동은 가장 매끄럽지만 셀프호스트·공개 재현성에서 불리), Arize Phoenix(검토 안 함).
- **주의**: Fortune 500 사용 수치는 Langfuse 자체 주장. Langfuse는 2026-01 ClickHouse에 인수됨(오픈소스 유지).

### 2026-10-28 — 사용자 정보는 처음에 다 묻지 않고, 필요할 때만 되묻는다
- **결정**: 에이전트가 답에 필요한데 모르는 정보(총급여·무주택/세대주·부양가족)만 그때 묻는다. 간소화 자료로 알 수 있는 지출은 묻지 않는다. 본인 제안(10/28)을 범위만 좁혀 채택.
- **이유**: ① "모르면 지어내지 않고 묻는다"는 **평가할 수 있는 동작**이 된다(평가 문항 4: 질문을 했나, 총급여 받기 전에 계산 툴을 부르지 않았나). ② 처음에 설문을 다 받으면 대화형 에이전트가 아니라 입력 폼이 된다.
- **버린 대안**: 시작 시 고정 설문(구현은 쉽지만 평가 포인트가 없고 사용성이 나쁨), 되묻기 없이 프로필 완비 가정(마일스톤 1까지만 이렇게 간다).
- **일정**: 마일스톤 3(11/11)에서 구현 + 평가.

### 2026-10-28 — 공제액 계산은 LLM이 아니라 코드(`calc_deduction`)가 한다
- **결정**: 금액 계산은 규칙 기반 함수 `calc_deduction`(2025 귀속 책자 규칙)이 하고, LLM은 ① 어떤 툴을 언제 부를지 판단 ② 결과를 사용자에게 설명하는 일만 맡는다.
- **이유**: ① LLM은 다단계 산술(25% 문턱 차감 순서, 한도 비교)에서 틀리기 쉽다. ② 계산이 코드면 **정답이 결정적**이라 정답 일치 평가와 회귀 테스트(pytest, CI)가 가능하다. 국세청 공식 사례(카드 530만원)를 첫 테스트로 쓴다. ③ 실패를 나눠 볼 수 있다 — 틀렸을 때 "툴 선택이 틀렸나 / 계산이 틀렸나 / 설명이 틀렸나"가 trace에서 분리된다.
- **평가로 확인하는 것**: 응답 속 금액 = `calc_deduction` 결과(규칙), 툴을 안 부르고 금액을 말하면 실패(문항 1·2).
- **버린 대안**: LLM이 규칙 문서(RAG)를 읽고 직접 계산(정답이 흔들려 평가 불가), 코드 실행 툴로 LLM이 계산식을 매번 작성(재현성 낮음).

### 2026-10-28 — 순서: 에이전트 + 평가(A안) 먼저 → 앱·실연동(B안)으로 확장
- **결정(본인 확정)**: 최종 그림은 "연말정산 앱 안의 에이전트 + 그 에이전트의 평가·관측". 지금은 에이전트와 평가 체계를 mock 데이터로 먼저 만들고(A안), 이후 데이터 출처를 실연동으로 바꾸고 앱 UI·배포를 붙인다(B안, 착수 시점은 정하지 않았다).
- **이유**: ① 평가셋·trace가 먼저 있으면 실연동으로 바꿀 때 **성능이 떨어졌는지 숫자로 확인**할 수 있다(회귀 평가). ② 고객 시스템 연동·배포와 평가·관측성을 한 프로젝트로 다룰 수 있다. ③ 개발 시간이 한정돼 프로젝트 2개를 병행할 수 없다.
- **지금 설계에 반영할 것**: 툴은 데이터 출처를 몰라야 한다 — `tools.py`는 `DataSource` 인터페이스만 호출하고, `MockDataSource`(지금)를 나중에 실연동 구현으로 갈아 끼운다. 이 경계 하나만 지키고 다른 확장 대비(앱 UI, 인증)는 지금 만들지 않는다.
- **버린 대안**: 앱부터 만들기(평가 기준 없이 연동부터 하면 품질을 말할 근거가 없음), 둘을 별도 저장소로 병행(시간 부족, 서사가 둘로 갈림).
