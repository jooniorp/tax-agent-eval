### 2026-10-15 — 데모 도메인: 세금 어시스턴트(연말정산)
- **결정**: 데모 에이전트의 도메인은 연말정산 공제 안내. 실연동 없이 mock.
- **이유**: 공제액은 규칙으로 계산되므로 **정답을 코드로 만들 수 있다** → 정답 일치 평가가 가능.
- **버린 대안**: 통신 고객센터 mock(정답 정의가 모호).

### 2026-10-15 — 프로젝트 축: 에이전트가 아니라 평가·관측성·비용
- **결정**: 에이전트는 단순하게, 측정 체계를 주인공으로.
- **이유**: 멀티 에이전트·RAG 자체는 흔한 주제다. 이 프로젝트가 보여 주려는 것은 평가·관측성·비용·배포다.
- **버린 대안**: 또 하나의 RAG 챗봇, 멀티 에이전트 데모.

### 2026-10-27 — 관측 도구: Langfuse (Cloud 무료로 시작 → 마일스톤 6에서 셀프호스트)
- **결정**: Langfuse. LangSmith는 쓰지 않는다.
- **기준**: "현업에서 더 많이 쓰는 것" (본인). 독립적인 점유율 조사는 없음 → 아래 신호로 판단.
- **이유**: ① 오픈소스·LangChain 비종속이라 어느 스택에서도 쓰인다(GitHub 약 2.9만 스타, 2026-06 기준 리뷰). LangSmith는 LangChain/LangGraph 스택 안에서 강함. ② 무료 셀프호스트 가능 — 데이터를 밖으로 내보낼 수 없는 환경(대기업·금융 등)에서도 쓸 수 있는 형태. LangSmith 셀프호스트는 Enterprise 애드온. ③ 마일스톤 6 "Docker 실행"에 그대로 포함 가능.
- **버린 대안**: LangSmith(LangGraph 연동은 가장 매끄럽지만 셀프호스트·공개 재현성에서 불리), Arize Phoenix(검토 안 함).
- **주의**: Fortune 500 사용 수치는 Langfuse 자체 주장. Langfuse는 2026-01 ClickHouse에 인수됨(오픈소스 유지).

### 2026-10-28 — 사용자 정보는 처음에 다 묻지 않고, 필요할 때만 되묻는다
- **결정**: 에이전트가 답에 필요한데 모르는 정보(총급여·무주택/세대주·부양가족)만 그때 묻는다. 간소화 자료로 알 수 있는 지출은 묻지 않는다. 본인 제안(10/28)을 범위만 좁혀 채택.
- **이유**: ① "모르면 지어내지 않고 묻는다"는 **평가할 수 있는 동작**이 된다(평가 문항 4: 질문을 했나, 총급여 받기 전에 계산 툴을 부르지 않았나). ② 처음에 설문을 다 받으면 대화형 에이전트가 아니라 입력 폼이 된다.
- **버린 대안**: 시작 시 고정 설문(구현은 쉽지만 평가 포인트가 없고 사용성이 나쁨), 되묻기 없이 프로필 완비 가정(마일스톤 1까지만 이렇게 간다).
- **일정**: 마일스톤 3(11/11)에서 구현 + 평가.

### 2026-10-28 — 공제액 계산은 LLM이 아니라 코드(`calc_deduction`)가 한다
- **결정**: 금액 계산은 규칙 기반 함수 `calc_deduction`(2025 귀속 책자 규칙)이 하고, LLM은 ① 어떤 툴을 언제 부를지 판단 ② 결과를 사용자에게 설명하는 일만 맡는다.
- **이유**: ① LLM은 다단계 산술(25% 문턱 차감 순서, 한도 비교)에서 틀리기 쉽다 `[2026-11-14 26문항 대조군에서는 틀리지 않았다. 2026-11-18 32문항 반복 측정에서는 대조군만 5/240번 틀렸다(계산기 0/240). 약하게 지지된다. 아래 두 항목 참고]`. ② 계산이 코드면 **정답이 결정적**이라 정답 일치 평가와 회귀 테스트(pytest, CI)가 가능하다. 국세청 공식 사례(카드 530만원)를 첫 테스트로 쓴다. ③ 실패를 나눠 볼 수 있다 — 틀렸을 때 "툴 선택이 틀렸나 / 계산이 틀렸나 / 설명이 틀렸나"가 trace에서 분리된다.
- **평가로 확인하는 것**: 응답 속 금액 = `calc_deduction` 결과(규칙), 툴을 안 부르고 금액을 말하면 실패(문항 1·2).
- **버린 대안**: LLM이 규칙 문서(RAG)를 읽고 직접 계산(정답이 흔들려 평가 불가), 코드 실행 툴로 LLM이 계산식을 매번 작성(재현성 낮음).

### 2026-10-28 — 순서: 에이전트 + 평가(A안) 먼저 → 앱·실연동(B안)으로 확장
- **결정(본인 확정)**: 최종 그림은 "연말정산 앱 안의 에이전트 + 그 에이전트의 평가·관측". 지금은 에이전트와 평가 체계를 mock 데이터로 먼저 만들고(A안), 이후 데이터 출처를 실연동으로 바꾸고 앱 UI·배포를 붙인다(B안, 착수 시점은 정하지 않았다).
- **이유**: ① 평가셋·trace가 먼저 있으면 실연동으로 바꿀 때 **성능이 떨어졌는지 숫자로 확인**할 수 있다(회귀 평가). ② 고객 시스템 연동·배포와 평가·관측성을 한 프로젝트로 다룰 수 있다. ③ 개발 시간이 한정돼 프로젝트 2개를 병행할 수 없다.
- **지금 설계에 반영할 것**: 툴은 데이터 출처를 몰라야 한다 — `tools.py`는 `DataSource` 인터페이스만 호출하고, `MockDataSource`(지금)를 나중에 실연동 구현으로 갈아 끼운다. 이 경계 하나만 지키고 다른 확장 대비(앱 UI, 인증)는 지금 만들지 않는다.
- **버린 대안**: 앱부터 만들기(평가 기준 없이 연동부터 하면 품질을 말할 근거가 없음), 둘을 별도 저장소로 병행(시간 부족, 서사가 둘로 갈림).

- **이유**: ① 설치된 langgraph 1.2.20에서 `create_react_agent`는 deprecated다(소스의 경고: `langchain.agents.create_agent`로 이동). 대체 함수를 쓰려면 `langchain` 패키지가 필요하다. (2026-11-07 갱신: Langfuse 핸들러가 어차피 `langchain`을 요구해 지금은 설치돼 있다. 그래도 이미 구현·테스트된 직접 구성을 유지한다.) ② 직접 만든 그래프는 약 20줄이라 구조가 코드에서 그대로 보인다. ③ `ToolNode`의 기본 설정은 툴이 던진 예외를 다시 던져 실행이 죽는다. `handle_tool_errors=True`로 오류를 모델에게 돌려준다 (`tests/test_agent.py`가 확인).

### 2026-11-07 — 트레이싱 연동: Langfuse `CallbackHandler`, 키가 없으면 자동 비활성
- **결정**: `langfuse.langchain.CallbackHandler`를 `ask(..., callbacks=...)`로 그래프에 넘긴다. `LANGFUSE_PUBLIC_KEY`·`LANGFUSE_SECRET_KEY`가 **둘 다** 있을 때만 켜지고(`src/tax_agent/tracing.py`), 없으면 langfuse를 import하지도 않는다. CLI는 종료 전에 `flush()`한다.
- **이유**: ① `agent.py`와 툴 코드는 langfuse를 모른다. 관측 코드는 호출하는 쪽(CLI, 나중엔 평가 러너)에서만 붙는다. ② 키가 없어도 개발·테스트가 그대로 돈다. ③ 설치된 langfuse 4.18.0이 LangChain 핸들러를 공식 제공한다. 이 핸들러가 LangGraph 실행의 모델·툴 호출을 기록하는 것은 2026-11-07 Langfuse API 조회로 확인했다(trace 1개에 모델 호출 3, 툴 호출 3). 핸들러는 `langchain` 패키지가 설치돼 있어야 import된다(키를 넣고 처음 실행했을 때 발견, `test_langfuse_handler_can_be_imported`가 막는다).
- **테스트 격리**: `tests/conftest.py`가 모든 테스트에서 Langfuse 키를 비우고 Anthropic 키를 가짜로 바꾼다. `.env`에 진짜 키가 있어도 테스트가 API 비용을 쓰거나 트레이스를 올리지 않는다.
- **발견 (2026-11-07) — 모델 호출이 2중으로 기록됨**: 첫 trace에 모델 호출마다 `ChatAnthropic`(LangChain 핸들러)과 `anthropic.messages.create`(Anthropic SDK 자체의 OpenTelemetry 스팬, scope `com.anthropic.sdk.python`)가 둘 다 생성됐다. trace 합계가 비용 $0.0016579, 토큰 8,314/1,653으로 실제의 2배였다. Langfuse 기본 필터가 `gen_ai.*` 속성이 있는 스팬을 모두 내보내기 때문이다. `should_export_span` 필터로 SDK 스팬을 제외했다(`tracing._should_export`, 테스트 있음). 핸들러 쪽을 남긴 이유는 추론(reasoning) 토큰을 출력에 포함해 실제 과금과 맞기 때문이다(SDK 스팬은 별도 항목). 수정 후 trace는 모델 호출 3개, 비용 $0.0008686, 토큰 4,131/911로 CLI 출력과 같다.
- **버린 대안**: 모델·툴 함수에 `@observe`를 직접 붙이기(핵심 코드에 관측 코드가 섞임), LangSmith(2026-10-27 결정 참고).
- **주의**: 트레이스에는 질문·툴 입출력·답변이 들어간다. 가상 데이터만 보내고, 실데이터(B안)를 붙일 때는 셀프호스트로 옮긴 뒤에 보낸다.

### 2026-11-10 — 평가셋 설계: 정답 일치 + 규칙 2방식, 10문항, 정답은 계산기가 만든다

- **시도하지 않은 대안(추정일 뿐 측정하지 않았다)**: 계산기 툴의 입력 형식만 줄이고 호출 수는 그대로 두기(비용이 대화를 다시 보내는 횟수에 비례하므로 효과가 작을 것으로 봤다), 프로필·데이터를 시스템 프롬프트에 미리 넣기(질문과 무관한 데이터가 항상 들어가고, 되묻기·없는 사용자 같은 경로를 평가하기 어려워질 것으로 봤다).
- **한계**: 한 모델(Haiku 5.5, 추론 기본 켜짐), 문항 32개, 문항별 3~5회. 통합 툴은 모델이 숫자를 옮기지 않으므로 "숫자가 중간에 바뀐다"는 실패를 재지 못하고, 규칙 검사의 종류와 개수가 다른 방식과 달라 "통과"가 완전히 같은 기준은 아니다. 통합 툴은 배치 1개(번갈아 실행 1회)로만 측정했다. 지연은 실행마다 편차가 커서 문항 단위 ±20% 이내는 잡음일 수 있다.
- **미결정이었던 것**: 기본 에이전트(`uv run tax-agent`)를 통합 툴로 바꿀지. 같은 날 소유자가 정했다(아래 항목).
- **다음 후보**: ① 추론을 끄거나 effort를 낮춘 설정에서 세 방식 비교, ② 다른 모델(더 작은 모델)로 같은 비교(마일스톤 5), ③ 프롬프트 캐시를 켰을 때 입력 비용 변화(통합 툴과 겹치는 효과인지), ④ 거절 표현 판정을 LLM-as-a-judge로.

### 2026-11-18 — 기본 에이전트를 통합 툴(`compute_deduction`)로 바꾼다 (소유자 결정)
- **결정**: `build_agent`, `uv run tax-agent`, `uv run eval`의 기본 변형을 `combined`로 한다(`agent.DEFAULT_VARIANT`). 단계별 툴(`calculator`)과 대조군(`no_calculator`)은 `--variant`/`--no-calculator`로 남겨 비교 기준으로 쓴다. `eval-compare`의 기준선도 계속 `calculator`다(저장된 결과와 비교하려고).
- **이유**: 같은 32문항에서 실패 0/120이면서 비용 -48%($0.0380 → $0.0196), 지연 -23%, 모델 호출 -42%였다(위 2026-11-18 측정 항목). 기본으로 바꾼 뒤 `uv run eval`을 한 번 돌려도 32/32 통과, 추정 $0.0197, 150.6초, 모델 호출 67회로 배치와 같았다(1회 실행).
- **잃는 것(알고 정했다)**: ① 모델이 숫자를 한 툴에서 다른 툴로 옮기지 않아 "숫자가 중간에 바뀐다"는 실패를 평가가 재지 못한다(`args_relayed` 검사 대응물 없음). 그 실패를 다시 재야 하면 `--variant calculator`로 돌린다. ② trace에서 프로필 → 데이터 → 계산기의 단계가 보이지 않고 `compute_deduction` 한 번의 입력(`user_id`, `item`, 사용자가 말해 준 값)과 결과(`inputs` 포함)만 남는다. 틀렸을 때 "조회 / 계산 / 설명" 중 어디가 문제인지는 결과의 `inputs`와 답변을 비교해서 가른다. ③ 통합 툴은 반복 측정이 배치 1개(번갈아 실행 1회)뿐이다.
- **같이 바꾼 것**: 실행 전 예상 비용 출력이 방식별 토큰 가정(`EST_TOKENS_PER_TURN`)을 쓰게 했다. 기본 방식의 예상이 실제의 약 2배($0.0374 대 $0.0197)로 나와서, 3방식 배치에서 문항당 평균을 다시 재서 올림해 넣었다.
- **버린 대안**: 기본은 그대로 두고 통합 툴을 옵션으로만 두기(데모와 평가의 기본 동작이 가장 비싼 쪽이 된다).

- **구조 결정**: 채널과 무관한 거래 계층을 먼저 만들었다(`src/tax_agent/transactions.py`). 어댑터가 `Transaction`(날짜, 금액, 가맹점, 결제수단, 분류)을 만들면, 연도별로 합산해서 계산기가 받는 입력(`CardSpending` 등)을 만들고 `DataSource`로 에이전트 툴에 붙는다. 분류가 안 된 거래와 제외 거래는 세지 않고 목록으로 보여 준다. 가상 거래로 테스트했고 mock 사용자 `user_a`의 입력을 거래로 풀어 쓰면 같은 공제액(5,300,000원)이 나온다. 채널이 바뀌어도 이 계층은 그대로다.
- **가장 현실적인 첫 채널(제안, 미확정)**: 소유자가 카드사·은행 앱에서 직접 내려받은 이용내역 파일(CSV·엑셀)을 `private/`에 두고 읽는 어댑터. 정기적으로 다시 내려받는 방식이라 "정기적" 요구는 수동으로 만족하고, "실시간"은 API 이용 조건이 확인된 뒤 같은 계층 앞에 붙인다. 파일에 가맹점·결제수단·업종이 어떻게 들어 있는지는 소유자가 샘플 형식(열 이름만, 값은 지우고)을 확인해 주어야 알 수 있다.
- **해결 안 된 것**: 거래를 공제 칸으로 나누는 분류(신용·체크 구분, 전통시장·대중교통·문화체육, 공제 제외 업종)는 파일에 담긴 정보에 달려 있다. LLM으로 분류할지, 규칙으로 할지는 정하지 않았다(LLM으로 한다면 정답이 붙은 가상 거래로 평가해야 한다). 의료비를 카드로 낸 경우 카드 공제에 중복으로 세는지, 기부금(계산기 없음)은 아직 다루지 않았다.
- **오픈뱅킹 OAuth 페이지 확인(소유자가 알려 준 `developers.kftc.or.kr/dev/openapi/open-banking/oauth`, 2026-11-18, 요약 도구로 읽은 것이라 원문과 대조 필요)**: ① 사용자 인증은 OAuth 2.0 Authorization Code Grant를 준용하고, 계좌실명조회 같은 사용자 없는 호출은 Client Credentials(2-legged)다. ② 클라이언트(이용기관의 앱)는 사용자의 계좌 정보를 직접 모아 등록할 수 없고, 사용자가 오픈뱅킹 등록 화면에서 동의·등록하면 클라이언트-사용자 쌍마다 24자리 핀테크이용번호가 나온다. ③ 자격에 관한 문구는 하나뿐이다. 이용기관이 오픈뱅킹에 가입하고 가입승인이 끝난 뒤 앱을 등록하면 클라이언트 ID와 시크릿을 받는다. 즉 **실계좌 API 키는 이용기관 가입승인 뒤에 나온다**. 개인이 이용기관이 될 수 있는지(사업자등록이 필요한지)는 이 페이지에 없다. 테스트베드는 개인 가입이 되지만 가상계좌로는 잔액·거래내역 조회가 안 된다(앞선 검색 결과). 결론: 본인 거래를 API로 받으려면 이용기관 승인이 선행되어야 하고, 개인이 가능한지는 금융결제원에 직접 확인해야 한다. 그때까지 첫 채널은 파일이다.

### 2026-11-19 — 합성 사용자 end-to-end 평가 (마일스톤 5.1, 둘째 단위)
- **한 일**: `uv run sim-agent`(`evaluation/sim_agent.py`). 합성 사용자의 거래를 분류기로 라벨링해 `TransactionDataSource`로 기본 에이전트에 붙이고, 카드·월세·의료비 질문 3개를 던진다. 질문마다 T(정답 분류로 계산한 공제액), C(분류된 거래로 계산한 툴 값), A(에이전트가 답한 금액)를 비교한다. 분류 오류는 C와 T의 차이, 에이전트 오류는 A와 C의 차이로 갈라 본다. 실행 전 예상 비용을 출력한다.
- **결과** (`claude-haiku-5-5` 기본 에이전트, 사용자 20명 × 질문 3개 = 60개, 이름 불분명 15%, 각 1회): 분류기가 키워드 규칙이면 종단 정확 26/60, 툴에 충실 60/60, 툴 값이 정답과 다른 질문 34/60, 비용 $0.032·242초. 모델 분류기(Haiku)면 28/60, 60/60, 32/60, $0.031·236초. **에이전트는 120/120번 툴 값을 그대로 전달**했고, 툴 값이 틀린 66개 질문에서도 모두 그 값을 따랐다. 병목은 분류다. 주제별 종단 정확은 카드 0/20·1/20, 월세 10/20·10/20, 의료비 16/20·17/20.

- **시뮬레이터의 한계 (결과 해석에 영향)**: 이름이 불분명한지를 거래마다 독립으로 정해서, 매달 나가는 월세가 한 번이라도 불분명한 이름일 확률이 약 86%다. 그래서 월세는 월세가 있는 사용자가 사실상 모두 틀리고(10/20은 정답 0인 사용자) 비관적이다. 실제로는 임대인 이름이 같다. 고치려면 사용자·가맹점 단위로 한 번만 정하게 해야 하는데, 그러면 난수 순서가 바뀌어 위 분류 평가 숫자도 다시 재야 해서 이번에는 한계로만 기록했다.
- **한계**: 사용자 20명, 질문별 1회, 한 모델. 지어낸 데이터라 절대 정확도가 아니라 층 분리(에이전트는 충실하고 오류는 입력 쪽)를 보여 준다. 사용자 정보를 프로필에서 받아 되묻기 경로는 이 평가에 없다.
